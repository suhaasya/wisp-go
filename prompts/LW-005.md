# Task LW-005: Budget gates: Go size and RAM, tab memory, bundle sizes
Milestone M0 (Foundations) · Priority P0 · Estimate 4 d · Step 5 of 48

## Your role
You are a senior engineer (Go, TypeScript and Preact) building Wisp, a local database client for PostgreSQL, MySQL and MariaDB. One Go binary serves a private HTTP server on 127.0.0.1 and the UI runs in the browser (Preact + TypeScript, built with Vite, styled with Tailwind CSS v4). Low memory for the Go process and for the browser tab is a deal breaker. Read AGENTS.md at the repository root before you start; its rules apply to this task.

## Goal
CI measures both budget tables on every pull request and fails when any deal-breaker value is exceeded.

## Why this matters
This ticket turns 'low memory' into a guarantee. Agents add libraries and caches casually; the gate catches it the same day.

## What to build (do these steps in order)
1. budgets.go: two slices of {Metric, Target, Cap, Unit} matching the PRD tables exactly.
2. Go RSS: read /proc/self/status VmRSS (Linux), task_info via golang.org/x/sys/unix (macOS), GetProcessMemoryInfo (Windows). Scenarios via --bench-scenario: idle (30 s after one SSE client connects), one_conn_500_tables, ten_connections, scroll_1m_rows. Unimplemented scenarios print status skipped.
3. make size: build for the host, report binary bytes and gzip/zip archive bytes; also read web/dist/sizes.json for JS/CSS gzip sizes.
4. Tab bench (tools/tabbench): Playwright launches Chromium, opens the app via the launch URL, uses CDP Performance.getMetrics (JSHeapUsedSize, Nodes) and Chrome's process memory (CDP SystemInfo.getProcessInfo or `performance.measureUserAgentSpecificMemory` where available) for scenarios: idle_connections_screen, open_table_scroll_1m (scroll to the end in steps), open_close_query_tab_x10. Also record long tasks via PerformanceObserver during scrolling.
5. tools/gate: merges results JSON, prints a table metric/value/target/cap/status, exits 1 on any cap breach; skipped never counts as passed.
6. CI job 'gate' on Linux (required) and macOS/Windows (Go side only): docker compose up, seed fixtures (500 tables, 1M-row table), make size bench gate, post sticky PR comment with the table.

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-005: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.
