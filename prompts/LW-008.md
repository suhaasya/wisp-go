## Goal
A small set of reusable, accessible Preact components styled with Tailwind tokens, plus a dev-only gallery page.

## Why this matters
Without a shared kit each screen would invent its own controls, growing the bundle and drifting from the design. Preact components with typed props keep agents consistent.

## What to build (do these steps in order)
1. Function components with typed props interfaces; no class components; no context except where noted. Use @preact/signals for component state that changes often.
2. Button variants default/primary/warning/ghost/danger; sizes sm/md; optional Kbd hint. Classes translate the mockup's .btn rules to tokens (e.g. 'border border-line bg-panel rounded-[7px] px-[11px] py-[5px] hover:bg-raise').
3. Input (text, password, mono), Select (native select styled), Segmented (aria-pressed buttons), Checkbox, Tabs (underline style), Modal (native <dialog> with showModal, Esc closes, focus returns to trigger), Toast (stack bottom-right, auto-dismiss, controlled by a toasts signal), Menu (context menu with keyboard), VirtualList (fixed row height, renders visible rows only; used by palette and tree), Tooltip.
4. Every effect that adds listeners or timers returns a cleanup; no global listeners outside effects.
5. Gallery route only in dev: `if (import.meta.env.DEV)` dynamic import so it is tree-shaken from production.

## UI specification

- Keyboard operable; visible focus ring.
- Use only Tailwind theme-token utilities (LW-007) and the Preact components in web/src/ui/ (LW-008); no arbitrary colour values, no new UI libraries.

## Acceptance criteria (every one must pass)
- Gallery renders every component in light and dark.
- Mounting and unmounting the gallery 1,000 times leaves no detached nodes or listeners (Playwright heap check).
- Kit adds ≤ 8 KB gzip to the initial bundle.

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-008: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.
