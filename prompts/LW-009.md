## Goal
The permanent frame of the page: hash router, typed API client with CSRF and abort support, one SSE connection for events, title bar with environment strip, and status bar with Go and tab memory meters.

## Why this matters
Every screen plugs into this shell. The SSE heartbeat also tells Go when the last tab closed (idle exit).

## What to build (do these steps in order)
1. Go SSE hub: GET /api/v1/events streams events {type, data}; heartbeat every 15 s; tracks connected clients and notifies lifecycle (idle exit) when count reaches 0; event types: session, query, progress, shutdown, reload (dev), memory.
2. Memory event every 5 s while a client is connected: Go RSS MB (from internal/bench RSS function).
3. Global state in web/src/state.ts as @preact/signals: settings, theme, currentSession, sessionState, toasts, goMemoryMB, tabMemoryMB. Screens read signals directly; no other state library.
4. api.ts: request(method, path, body, {signal}) adding X-Wisp-CSRF from /hello, JSON in/out, error objects {code, message, detail}; 401 shows a 'Session ended, relaunch wisp' screen.
5. events.ts: EventSource wrapper with reconnect backoff; 'shutdown' and failed reconnect show a banner 'Wisp stopped. Run wisp to continue.'
6. router.ts: #/connections, #/connections/new, #/connections/:id/edit, #/w/:sessionId (workspace). A route signal selects the screen component; unmounting a screen runs its effect cleanups.
7. Title bar (40 px): app name or env pill + connection name + 'user@host via SSH' (ink-2), palette button with Ctrl/⌘K hint on the right, 2 px env strip at the bottom (transparent when no connection).
8. Status bar (26 px): left slot (env dot, read-only flag, server version, latency), right slot: 'Go 18 MB' and 'Tab 4 MB' meters (tab = performance.memory.usedJSHeapSize where available, otherwise hidden).

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-009: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.

## Final report
End with the report format from AGENTS.md section 8: summary, files changed, confirmed seams and the tests written for each, each acceptance criterion with PASS/FAIL and evidence, measurements, dependencies added, refactor ideas, open questions.
