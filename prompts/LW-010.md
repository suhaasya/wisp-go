## Goal
Settings persist in a small JSON file, load instantly, and apply live in the page.

## Why this matters
Theme, density, grid page size and safety defaults are read by many tickets; one store and API avoids duplication.

## What to build (do these steps in order)
1. Settings struct (see interface) with defaults; file config/settings.tson; missing keys take defaults; unknown keys preserved.
2. Atomic save: write temp file, fsync, rename; file mode 0600.
3. GET/PUT /api/v1/settings; PUT validates ranges and returns the stored settings; emits an SSE 'settings' event so other tabs update.
4. Page: settings.ts caches settings, applies theme and density on change.

## Files to create or change
- internal/store/settings.go (+ test)
- internal/api/settings.go
- web/src/settings.ts

## Interface to implement (adapt names if needed; keep the shape)
```go
type Settings struct {
  Version int; Theme string /* light|dark|system */; Density string /* compact|comfortable */
  WindowRows int /* default 150 */; WindowsInMemory int /* default 3 */; ResultCapMB int /* default 32 */
  KeepAliveSec int /* 60 */; IdleExitMin int /* 10 */; GoMemLimitMB int /* 64 */
  ConfirmWritesOnProduction bool /* true */; Keybindings map[string]string; Telemetry bool /* false */ }
```

## Acceptance criteria (every one must pass)
- Deleting settings.json restores defaults without error.
- Invalid JSON keeps last good settings and returns a clear error to the page.
- Changing theme in one tab updates other open tabs.

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-010: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.
