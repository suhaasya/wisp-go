## Goal
Create and edit connections in a tabbed form with validation, a Test button with precise errors, and a Go-served file picker for keys and certificates.

## Why this matters
Browsers hide real file paths, so Go provides a small home-scoped file picker. Precise test errors decide whether users trust the tool.

## What to build (do these steps in order)
1. Sheet 640 px centred: header (title + URL paste row, wired in LW-018), tabs General / SSH tunnel / SSL / TLS / Advanced, footer (test result line + Test, Save, Save and connect).
2. General tab 6-column grid as in the screenshot: Database type segmented, Name + Folder, Connect using (Host and port active; Socket and Named pipe disabled until LW-043), Host + Port, User / Password / Database, Save password checkbox, Environment picker, Read-only and Confirm every write.
3. Engine sets default port only if the port was not edited. Production pre-checks Confirm every write.
4. Advanced tab: default schema, session time zone, statement timeout, keep-alive, run on connect.
5. Validation inline; Test posts the unsaved form to /connections/test (10 s timeout, cancellable) and shows 'Connected in 42 ms · PostgreSQL 16.4, TLS 1.3, via SSH' or a mapped error.
6. Error mapping in Go: DNS failure, refused, timeout, auth failed, unknown database, TLS required/mismatch, SSH failures → one plain sentence + technical detail.
7. File picker: GET /fs/list?path=~/... lists directories and files under the user's home only (reject paths outside after filepath.Clean and symlink resolution); UI modal with breadcrumb, filter, Select.

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-017: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.
