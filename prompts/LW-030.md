## Goal
Show the exact SQL for staged changes, run it in one transaction, and add extra friction on production.

## Why this matters
This is the product's core safety promise: nothing changes until the user has seen the SQL.

## What to build (do these steps in order)
1. Generate DELETE, UPDATE (changed columns only, WHERE pk), INSERT with bound args; optional optimistic mode adds original values to WHERE.
2. Display rendering from the same generator with literals inlined via dialect.QuoteLiteral (one code path).
3. GET .../changes/sql returns the display SQL and counts; POST .../changes/commit runs in one transaction; on error rollback and return the failing statement index and DB message.
4. Optimistic conflict: UPDATE affecting 0 rows → rollback and report 'Row X was changed by someone else'.
5. Dialog 620 px: title 'Review N changes to <table>', subtitle with connection and environment, coloured SQL, 'Nothing is written until you commit.', Keep editing / Commit changes.
6. Production or safe-mode deletes: typed confirmation of the table name before commit.
7. Shortcuts: Ctrl/⌘+S opens review; after success: clear change set, refresh windows, toast with counts.
8. Warn on MySQL MyISAM tables (no rollback).

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. 5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-030: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.
