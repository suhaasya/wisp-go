## Goal
The first screen: saved connections as cards grouped by folder, with search, environment filters and one-click connect.

## Why this matters
It must make each connection's environment obvious at a glance and render instantly.

## What to build (do these steps in order)
1. Layout: left rail 210 px (folders with counts, environment filters with coloured dots), main area padded 22×28 px, scrollable.
2. Top row: search input (max 360 px), New connection (primary, Alt+N), Import (disabled, tooltip 'Coming in v1.1').
3. Hint line: 'Paste a URL anywhere to create a connection' with an example in mono.
4. Cards (grid auto-fill min 250 px, gap 12): 4 px env-colour left edge, engine badge 26×26 (PG #336791 → add tokens badge-pg/badge-my/badge-mdb), name semibold, host mono 11.5 px truncated, tag chips, last used or Production pill.
5. Double-click or Enter opens a session (POST /sessions, LW-021) then routes to the workspace; context menu: Edit, Duplicate, Move to folder, Delete (confirm).
6. Client-side fuzzy filter over name, host, tags; rail filters combine with search.
7. Empty state with New connection and paste hint.

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-016: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.

## Final report
End with the report format from AGENTS.md section 8: summary, files changed, confirmed seams and the tests written for each, each acceptance criterion with PASS/FAIL and evidence, measurements, dependencies added, refactor ideas, open questions.
