# Task LW-044: Browser compatibility and accessibility pass
Milestone M4 (Release) · Priority P0 · Estimate 3 d · Step 44 of 48

## Your role
You are a senior engineer (Go, TypeScript and Preact) building Wisp, a local database client for PostgreSQL, MySQL and MariaDB. One Go binary serves a private HTTP server on 127.0.0.1 and the UI runs in the browser (Preact + TypeScript, built with Vite, styled with Tailwind CSS v4). Low memory for the Go process and for the browser tab is a deal breaker. Read AGENTS.md at the repository root before you start; its rules apply to this task.

## Goal
The app works and meets the tab budgets in current Chrome, Edge, Firefox and Safari, and every P0 flow is keyboard accessible.

## Why this matters
Each browser differs in memory reporting, clipboard and shortcut handling; check them all before release.

## What to build (do these steps in order)
1. Run Playwright e2e suites on Chromium, Firefox and WebKit.
2. Measure whole-tab memory manually in each browser's task manager; record and adjust only the whole-tab budget row if needed (with the PRD owner).
3. Audit focus order, visible focus, ARIA roles for grid, tree, tabs, dialogs; labels on all inputs.
4. Respect prefers-reduced-motion and OS font scaling.

## How to work
Follow the TDD skill (.claude/skills/tdd/SKILL.md) and AGENTS.md section 6.
1. First reply with a plan: files you will touch, approach per step, and how each acceptance criterion will be proven.
2. In the same reply, list the seams you propose to test (start from the section above). For each: the public interface, one line on what it catches, one line on what it misses. Then STOP and wait for me to confirm the seams. Do not write any test or code before that. (If this ticket has no code under test, say so and continue.)
3. After confirmation, work in vertical slices: one seam, one failing test (red), the minimal code to pass it (green), run the tests, commit. Repeat. Never write all tests first.
4. Test only through public interfaces; fake only system boundaries (database, network, clock, filesystem). Expected values come from the spec or literals, never recomputed like the code does.
5. Do not refactor inside the loop; collect refactor ideas for the report.
6. Commit messages start with the task id (e.g. "LW-044: add ..."). If the task conflicts with AGENTS.md, docs/PRD.md or existing code, stop and explain instead of guessing. Do not start the next ticket.

## Final report
End with the report format from AGENTS.md section 8: summary, files changed, confirmed seams and the tests written for each, each acceptance criterion with PASS/FAIL and evidence, measurements, dependencies added, refactor ideas, open questions.
